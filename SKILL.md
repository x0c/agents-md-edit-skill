# AGENTS.md Edit

Improve the decisions future agents make. Preserve behavior, scope, exceptions and discoverability; brevity alone is not success, and neither is unrequested growth. Explicitly read-only reviews never write files.

## A bounded change

1. Identify the requested decision, its existing authority and overlapping rules. Read that domain, relevant links, and [decision criteria](references/decision-criteria.md). Restate the user's actual words before writing: they bound what may be written.
2. Size the rule to the decision. A one-line decision becomes one line of rule — a table row or a short sentence stating the decided action with its trigger, plus at most one pointer to detail — never the mechanism, incident, or warnings, whether they decided the action or merely restate its stated priority. The reader is a model, not a person: what a competent model can derive on its own — standard commands, tool-class behavior, error and address-range meanings, causal mechanisms and symptom fingerprints, standard recovery after a confirmed finding — is not information; a recovery order or side effect that is itself a local fact stays. Draft at minimal form: a candidate clause survives only as the decided action, its trigger, a fact a model cannot infer (which tool, which account, which port, which path, which mode, which numbers or timing), or detail the user explicitly requested; drop the rest — recurrence and blame (who tripped it, how often, why it repeats) are incident, not fact. Draft at the size of the decision, not the style or register of neighboring rules or remembered incidents. Capture guidance embedded in the target file governs what belongs in the owning records it names; whether and how much enters this file is decided by the user's request and this skill. Operational detail (commands, install procedures, recovery steps, paths, version checks, output contracts, tool quirks, tool-comparison conclusions) lives in the tool's own doc or skill, never in a default-loaded file — unless the user explicitly requested it in this file, which outranks both placement and omission; a path that identifies a thing stays, a path that tells how to operate is procedure; naming the cause is scope, telling how to fix it is procedure; a usage precondition the user's own words stated is decided content, not fix; if no owning doc exists, omit the detail and name the missing destination in your report — having nowhere to relocate it never justifies inlining. Absence of prohibition is not authorization: verified detail, denser neighboring entries, or a future agent's imagined confusion justify nothing beyond the decided content.
3. Update one authoritative home. Reconcile conflicts using current user intent and evidence. Change generated text through its maintenance source. Do not promote a temporary example, frustration or runtime instruction into permanent policy.
4. Describe document contents in navigation. Requirements must be discoverable before ordinary implementation without the user naming their keywords. Keep the shared relevance instruction; remove stale trigger catalogs and reading quotas within the authorized scope.
5. Audit the addition, not only the preservation. List every new clause and ask one question: did the request itself decide this? Notes, tests and prior investigation prove content true, never that it belongs in the file — provenance is not authorization. Delete or relocate whatever the request did not decide; treat scope exceptions and boundaries as detail unless the decided content or an existing rule states them. Only user-ruled content may carry a user-decision marker; never stamp agent analysis or findings as the user's ruling.
6. Re-read the affected domain and references. Compare the resulting action on an ordinary task, an exception and an unrelated task in both directions: no adopted behavior lost, and no unauthorized rule gained. Then apply a deletion test to every new sentence: remove it; if no future action changes, it stays deleted — a stated priority needs no warning against the alternative it displaced, unless the user's own words — not the source notes — name the displaced alternative. Compression may remove words, never applicability, timing or adopted constraints.

## A whole-file review or cleanup

Read [decision criteria](references/decision-criteria.md). Read the full file and design its structure around decision ownership rather than inherited headings. Inventory every domain's issues and assign retain, merge, move, route, remove or unresolved dispositions. Dispositions classify rules; density governs their text: every retained rule is re-drafted through the step 2 reader filter, minimal form and deletion test — retention never means verbatim, and a command string, trigger enumeration or warning that step 2 would not draft into the file leaves during cleanup unless cutting it would lose an uninferable local fact or an adopted constraint. Verify the destination of moved material; do not leave the lower body outside the review.

For a review, report concrete issues and representative revised wording. For cleanup, integrate the changes and check every retained behavior's home, reachability and applicable exceptions. Compare measured default-loaded size before/after (token figures are estimates); explain justified growth without treating a target as the criterion.

## Structural checks

Run `python3 scripts/audit.py PATH --json` from this skill directory, or use its absolute script path. Read [audit coverage](references/audit.md) when interpreting the report. Inspect coverage before findings: zero identified index sections or links does not establish valid navigation. A clean report does not prove semantics or execution quality.
